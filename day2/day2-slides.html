The Terminal

Twenty minutes to make the black window feel ordinary. If you've never opened one, this part is for you — and you are not the only one.
Opening it Reading it Four commands The escape hatch
Roughly a quarter of the room has never opened a terminal. Say that out loud - it makes it safe to be a beginner and stops people pretending they're fine.
Reminder from yesterday

Same computer. Same files. Different way of asking.

Pointing — what you know

You see folders and icons. You move the mouse, double-click, drag things around.

You point at what you want.

Typing — the terminal

The very same folders and files. But you type a line describing what you want, and press Enter.

You describe what you want.

Reassurance

The terminal is not a special "programmer mode" that can damage your computer. It's a different door into the same house. Everything we type today is safe, and you can close the window at any time.

The fear here is real and usually unspoken - people think the terminal is where you break things. Address it directly before asking anyone to open one.

Before you type anything

What all that text on the first line means

terminal
Windows C:\Users\Nimal> ▊ Mac nimal@MacBook ~ % ▊
  1. 1
    Your name and machineJust a label. Nothing to do with what you type.
  2. 2
    Which folder you're inThis is the useful part. The terminal is always "standing" inside one folder.
  3. 3
    The symbol — > or %Means "ready, type here". You never type this symbol yourself.
  4. 4
    The blinking cursorWhere your typing appears. That's all it is.
Point three matters more than it looks - beginners routinely copy the prompt symbol into their command and then get a confusing error. Say it explicitly.
Do now · Step 2

Two commands: where am I, and what's here

Do now Type each one, press Enter, see what happens
Windows
> cd shows the folder you're in > dir lists what's inside it
Mac
% pwd shows the folder you're in % ls lists what's inside it
You should see A folder path, then a list of names — probably Documents, Downloads, Desktop and similar. These are the same folders you'd see in a file window.
The realisation to draw out loud: these are the same folders they already know, just listed as text. That connection is what makes the terminal stop feeling alien.
Do now · Step 3

Make a folder and step into it

Do now Same commands on both Windows and Mac
> mkdir my-agent ← make a new folder > cd my-agent ← step inside it > cd .. ← step back out again > cd my-agent ← and back in. This is where we work today.
You should see The folder name at the start of your line changes as you move in and out. That text always tells you where you are.
✋ Checkpoint

Everyone should now be inside a folder called my-agent. Check the start of your line says so.

Everything for the rest of the day happens inside this folder, so this checkpoint genuinely matters. Anyone in the wrong place will hit confusing errors later.
Your safety net

Ctrl + C stops anything

If text is scrolling forever, if something seems stuck, if you simply want out — hold Ctrl and press C. It stops whatever is running and gives you back your prompt.

It's safe

Ctrl + C cannot damage anything. It's a stop button, not a delete button.

Same on both

Windows and Mac. It's Ctrl, not Cmd, even on a Mac.

Use it freely

Any time today you feel stuck, press it and tell me what you saw.

Give everyone permission to use this constantly. Knowing there is an escape hatch is what lets nervous people experiment instead of freezing.

Setting Up

Thirty-five minutes to get a working coding agent on your own laptop. Six steps, one at a time, nobody left behind.
Install Node Check it Install OpenCode Get a free key Connect First prompt
This is the highest-risk section of the whole week - installs fail in ways you cannot predict. Budget generously and keep the troubleshooting slide handy.
What we're installing

Two separate pieces, and why

Why it's split

Your files never leave your laptop unless the agent sends a piece of them as part of a question. And because the brain is separate, a better model next year means changing one setting — not relearning everything.

Somebody always asks where their files go. Answer it here, before it becomes a worry: the agent runs locally, only the relevant context travels.

Do now · Step 2 of 6

Check it worked

Do now Close your terminal, open a NEW one, then type these
> node -v v20.11.0 ← a version number, yours may differ > npm -v 10.2.4 ← another version number
The point The exact numbers do not matter at all. Seeing a number instead of an error is the entire test.
✋ Checkpoint

Hands up if either command said "not recognized" or "command not found". That almost always means the terminal was open before you installed — close it, open a fresh one, try again.

The stale-terminal problem catches a large chunk of any room. Emphasise the "close and reopen" instruction before they type, not after they fail.
Do now · Step 3 of 6

Install OpenCode

Do now One command — identical on Windows and Mac
> npm install -g opencode-ai
You should see Lines of text scrolling for up to a minute, ending with a summary of what was added. Warnings in yellow are normal and can be ignored — only red errors matter.
What -g means

The -g is short for "global" — install it for the whole computer, not just this one folder. That's why you can then run it from anywhere.

Yellow warning text frightens beginners. Tell them in advance that yellow is normal, so they don't all raise hands at once during the install.
Do now · Step 4 of 6

Get your own free Gemini key

Do now In your web browser, not the terminal
1. Go to aistudio.google.com/apikey 2. Sign in with your Google account 3. Click Create API key 4. Copy the key it gives you
You should see A long string of letters and numbers. Copy the whole thing — a missing character is the most common problem in the next step.
Treat it like a password

This key is yours alone and it's free — no credit card is requested at any point. Don't post it anywhere or share it. If you ever lose it, you just create another.

Each person must make their own key - a shared key would hit rate limits instantly with a room this size. Watch for anyone trying to copy a neighbour's.
Do now · Step 5 of 6

✋ Checkpoint

Everyone should now see a confirmation that Google is connected. Hands up if you saw an error instead.

The invisible-paste behaviour causes real panic - people paste, see nothing, and paste four more times. Warn them before they try it.
Do now · Step 6 of 6

You should see The agent thinking, then creating the file, then printing back what it wrote. Type dir or ls afterwards and you'll see hello.txt sitting there.
✋ Checkpoint

This is the big one. Everybody should now have a real file, created by an agent, on their own laptop. Hands up if not — we fix it before going further.

This is the emotional high point of Day 2. Let the room enjoy it for a moment before moving on - many will have just made software do something for the first time.
Expected problems

Three things that will happen to somebody today

What you seeWhat it meansWhat to do
not recognized Terminal was open before you installed something. Close it, open a new one, try again.
429 / rate limit Too many tokens sent too quickly — remember those from yesterday. Nothing is broken. Wait a minute, then carry on.
invalid API key The key was pasted with a missing or extra character. Run /connect again and paste it carefully.
The universal fix

For anything not on this list — copy the whole error message and paste it to your agent, with a line saying what you were trying to do. Reading errors is exactly what it's good at.

Teaching them to paste errors back to the agent is the single most valuable troubleshooting habit of the week. It scales past anything you can personally support in a room of eighty.
Two minutes of insurance

Make a second key now, while it's calm

Free keys have daily limits. On Day 4 we'll all be working hard at the same time, and somebody will hit theirs. A spare key turns a stuck afternoon into a thirty-second fix.

Do now Same page as before — make one more
1. Back to aistudio.google.com/apikey 2. Click Create API key a second time 3. Save both keys somewhere you can find them — a note on your phone is fine
This slide exists because of a real risk on Day 4. Two quiet minutes now prevents several stalled people later in the week.

Teaching Your Agent

You have a working agent. Now you'll give it three things that make it genuinely yours — the standing rules, a shortcut, and a borrowed method.
AGENTS.md Your first command Using a skill Making a skill
Everything from here is the pay-off for the setup grind. The energy in the room usually lifts here - lean into it.
Thing 1 of 3 · Why

Stop repeating yourself in every prompt

Without AGENTS.md

"Add a page. Remember, plain HTML, no frameworks, keep files in this folder, ask before installing…"

Typed again. And again. And again.

With AGENTS.md

"Add a page."

The background is in a file the agent reads before every task, automatically.

Remember

The note you leave for a substitute teacher. Written once, so you don't explain it every morning.

Quick recall from Day 1, not a re-teach. Thirty seconds, then straight into writing one.
Thing 1 of 3 · Do now

Ask your agent to write it for you

Do now Type this to your agent
> create an AGENTS.md file for this project. Stack: plain HTML and CSS, no frameworks. Rules: keep all files in this folder, use simple language in comments, and ask me before adding anything new.
Then check it Type dir on Windows or ls on Mac — AGENTS.md should now be listed. Ask the agent to show you the contents if it doesn't automatically.

Your file should look close to this. It doesn't have to match word for word.

AGENTS.md

Show the file on screen and let people compare. Two things to say: theirs will differ slightly and that is fine, and they never opened an editor - they described a file and the agent wrote it. That is the loop already working for them.

This is the moment AGENTS.md becomes real rather than theoretical - but only if they can see it. Walk the three cards one at a time and have people confirm each against their own screen, rather than just asserting it happened.
Thing 2 of 3 · Why

A command is a text file whose name is the shortcut

AGENTS.md is background that always applies. A command is an action you fire when you want it. Both are just files — this is the one you saw yesterday.

.opencode/commands/course-outline.md
--- description: Create a short course outline for a topic argument-hint: [topic and year group] --- Write a one-page course outline for: $ARGUMENTS Include who it is for, 3-5 learning outcomes, 4-6 sessions, and one way to check they learned it.
  1. 1
    The filename is the shortcutcourse-outline.md gives you /course-outline
  2. 2
    The top part is just a labelA reminder of what it does and what to type after it. Both optional.
  3. 3
    $ARGUMENTS is the blankWhatever you type after the name drops in here. This is what makes one file work for every topic.
  4. 4
    The rest is plain EnglishExactly what you'd otherwise type each time — and you can email the file to a colleague.
$ARGUMENTS is the idea that makes commands click, so spend your time there. Without it a command is a fixed paragraph; with it, one file serves every topic they will ever teach. They saw this exact file yesterday - say so, it builds continuity.
Thing 2 of 3 · Do now

Create your own command

Do now Ask the agent to make the file
> create a command called course-outline. It should write a one-page course outline for whatever topic and year group I give it, with who it is for, 3 to 5 learning outcomes, 4 to 6 sessions, and one way to check they learned it. Use $ARGUMENTS for the topic.
You should see A new file at .opencode/commands/course-outline.md. The dot at the front simply means the folder is normally hidden — nothing unusual about it.
Then check it Ask: "show me the file you just created" and compare it with the previous slide.
Notice

You asked for $ARGUMENTS by name. That one word is the difference between a command that only writes about spreadsheets and one that writes about anything you type after it.

Explain the leading dot before someone panics about a folder they cannot find in their file browser. If anyone's agent left out $ARGUMENTS, have them ask it to add it - a good small example of correcting rather than starting over.
Thing 2 of 3 · Use it

One file, every topic you'll ever teach

Do now Run it twice — with two different topics
> /course-outline spreadsheets, Grade 10 then run it again with something else — > /course-outline internet safety, Grade 7
You should see Two completely different outlines, both in the same shape — and you typed the instructions zero times.
✋ Checkpoint

Everyone should have two outlines on screen from one file. Try a topic you're actually teaching next term — this is a tool you can use on Monday.

Running it twice is the whole point of this slide - one run proves nothing about reuse, two runs make $ARGUMENTS visible. Then invite two or three people to say what topic they chose and whether the outline was any good.
Thing 3 of 3 · Building one

A skill is a method, saved as a file

A command saves an instruction. A skill saves a whole method — the steps to follow for a kind of job. Let's build the one from yesterday, then watch it change how your agent behaves.

Do now Ask the agent to create the skill
> create a skill called idea-refine. Its method: ask me 3 to 5 short questions, offer two or three directions, then write a one-page specification. Rule: never skip the questions.
You should see A new folder with a SKILL.md inside it — .opencode/skills/idea-refine/SKILL.md
.opencode/skills/idea-refine/SKILL.md
--- name: idea-refine description: Turn a rough idea into a clear one-page specification by asking questions first --- ## What I do ## Rules - Ask 3-5 questions - Never skip the questions - Offer directions - Keep it to one page - Write the spec
Building the skill before using it matters - it removes any doubt about whether the skill exists, and they see the file with their own eyes first. Only two lines are truly required: name and description. Everything under them is just markdown they wrote.
Thing 3 of 3 · Using it

Now watch your own file change its behaviour

You never mention the skill by name. The agent reads the description, recognises the job, and follows your method by itself.

Do now Ask for help with a rough idea
> help me refine an idea for a classroom activity about online safety
Watch for It should ask you questions instead of answering — because your file told it to. Answer them and let it write the specification.
✋ Checkpoint

Questions coming back instead of an instant answer? That's your own skill file steering the agent. If it answered straight away, tell it: "use the idea-refine skill".

The behaviour to highlight is the questioning - beginners expect instant output, and a skill deliberately slows things down for a better result. The checkpoint has the fallback in it: if a model does not pick the skill up on its own, naming it explicitly always works, so nobody gets stranded.
Part 4 of 4

The Workflow

One method for building anything bigger than a single request — and the exact method you'll use to build a real application on Day 4.
idea-refine write-prd planning-and-task-breakdown Iterate
Frame this as the bridge to Day 4. Today they run it on teaching material; Thursday they run the identical pipeline on software.
The method

Never ask for something big in one go

Asking for a whole project in one sentence gives you a vague result. Four smaller steps give you something you actually wanted — and there is a skill for each step, so you don't have to remember how.

The key insight to say aloud: each arrow is a chance to catch a misunderstanding while it is still cheap to fix. That is the entire reason for the pipeline.
Do now · Before we start

Give your agent the other two skills

You built idea-refine a few minutes ago. You need one skill per stage — so let's make the remaining two. You already know how, so this is quick.

Do now One prompt creates both
> create two more skills. write-prd — takes a refined idea and writes a one-page PRD with six sections: what we are building, who it is for, why, what it must do, what we are NOT doing, and how we know it is done. planning-and-task-breakdown — takes a PRD and turns it into 4 to 8 numbered tasks, each with a Do line and a Done line.
Then check Ask: "list my skills" — you should have three.
.opencode/skills/
idea-refine/SKILL.md ← step 1 write-prd/SKILL.md ← step 2 planning-and-task-breakdown/SKILL.md ← step 3
Deliberately fast - they learned the mechanic slowly when they built idea-refine, so this is just applying it. The folder listing is the point: three skills, one per stage of the pipeline they are about to run. Anyone whose agent only made one skill should ask it for the missing one.
Do now · Pipeline step 1

Turn a rough idea into a specification

Do now Pick something you'd genuinely like for your class
> use the idea-refine skill on this idea: a set of revision materials for my Grade 10 ICT class on spreadsheet formulas
Watch for It asks 3 to 5 questions, then offers two or three different directions and recommends one. Answer honestly and pick a direction — the questions are the valuable part.
This is Interview Style

Technique 6 from yesterday — make it ask you first. The skill just saves you having to remember to do it.

Naming the skill explicitly is what makes this reliable - the agent may pick it up on its own, but saying the name never fails. Encourage a genuine need rather than an invented example; people engage far more when the output is something they will actually use.
Do now · Pipeline step 2

Sharp idea → a PRD

A PRD — product requirements document — is just a written agreement about what you're making, before anyone starts making it.

Do now Feed your refined idea into the next skill
> now use the write-prd skill to turn that into a PRD
You should see A one-page document with six sections. Section 5 is the one to read carefully.
1–3

What we're building, who for, and why it's worth doing.

4

What it must do — each item checkable, yes or no.

5–6

What we're not doing, and how we'll know it's done.

Section 5 - what we are not doing - is the one that saves them. It is what stops a piece of work quietly growing until it never finishes. Ask someone to read theirs out loud; it is usually the moment the value of a PRD lands.
Do now · Pipeline step 3

PRD → tasks you can actually start

Do now The last skill in the chain
> use the planning-and-task-breakdown skill on that PRD
You should see 4 to 8 numbered tasks, in order, each with a Do line and a Done line — so you can always tell what finished looks like.
what comes back
Task 1 — Write the practice questions Do: 10 questions on formulas, easy to hard Done: 10 questions exist with an answer key Task 2 — Add a worked example for each Do: show the steps, not just the answer Done: every question has a worked example
This is Least-to-Most

Technique 5 from yesterday. You've now used three skills in a chain, and each one handed its result to the next.

The Do/Done shape is what makes tasks real - without a Done line you cannot tell whether you have finished. Stress reading the tasks before accepting them: correcting a task list takes a sentence, correcting finished work takes the whole build again.
Pipeline step 4

Iterating is the job, not a sign of failure

What beginners do

The output isn't right, so they delete everything and start the whole request again from scratch.

Slow — and it throws away the parts that were fine.

What you do now

"Good, but the questions are too easy for Grade 10, and I need a marking scheme at the end."

Keeps everything that worked. Changes only what didn't.

The rule of the week

Don't start over. Say what's wrong. This is the same rule from Day 1, and you'll rely on it heavily on Day 4.

Third time this rule has appeared across the course, deliberately. Repetition is what makes it a reflex by Thursday.
