Part 1

The Terminal

Twenty minutes to make the black window feel ordinary. If you have never opened one before, this part is written especially for you.

What it is, one more time

The terminal is the same computer and the same files you already know — just a different way of asking for things. Instead of pointing at an icon with your mouse, you type a line describing what you want and press Enter.

Reassurance

The terminal is not a special "programmer mode" where you can damage your computer. It's a different door into the same house. Everything we type today is safe, and you can close the window whenever you like.

Step 1Open your terminal
Windows
Press the Windows key Type: powershell Press Enter
Mac
Press Cmd + Space Type: terminal Press Enter
You should see A window with some text and a blinking cursor waiting for you to type.

Reading that first line

Before typing anything, it helps to know what the text already on screen means.

terminal
On Windows C:\Users\Nimal> On Mac nimal@MacBook ~ %
  1. 1
    Your name and machineJust a label. Nothing to do with what you type.
  2. 2
    Which folder you are inThis is the useful part — the terminal is always "standing" inside one folder, and this tells you which.
  3. 3
    The > or % symbolMeans "ready, type here". You never type this symbol yourself — in this guide it only shows where a command begins.
Step 2Where am I, and what's here?
Windows
> cd shows your current folder > dir lists what's inside
Mac
% pwd shows your current folder % ls lists what's inside
You should see A folder path, then a list of names — Documents, Downloads, Desktop and so on. These are exactly the folders you'd see in a normal file window.
Step 3Make a folder and step into it

These four are identical on Windows and Mac.

> mkdir my-agent ← make a new folder > cd my-agent ← step inside it > cd .. ← step back out > cd my-agent ← and back in
Watch The folder name at the start of your line changes as you move in and out. That text always tells you where you are.
✋ Checkpoint

You should now be inside a folder called my-agent. Everything for the rest of today happens in here — if you're somewhere else, later steps will give confusing errors.

Your escape hatch: Ctrl + C

If text scrolls forever, if something seems stuck, or if you just want out — hold Ctrl and press C. It stops whatever is running and gives you back your prompt.

  • It's safe. Ctrl + C is a stop button, not a delete button. It cannot damage anything.
  • It's the same on both systems — and on a Mac it really is Ctrl, not Cmd.
  • Use it freely. Any time you feel stuck today, press it and put your hand up.
Part 2

Setting Up

Six steps to a working coding agent on your own laptop. Take them one at a time and check each one before moving on.

What we're installing, and why it's two pieces

  • OpenCode — the agent itself, running on your laptop. This is the part that reads, writes and runs your files.
  • A Gemini API key — your personal pass to Google's AI model, which does the thinking. Free, and no credit card is requested.

Your files stay on your own machine. Only the relevant piece of context travels to the model as part of a question — and because the two are separate, switching to a better model later means changing one setting, not relearning everything.

Step 1Install Node.js

Node is the engine OpenCode runs on. Install it once and forget about it. Go to nodejs.org and download the version marked LTS — that stands for Long Term Support and it's the stable one.

Windows
Download the .msi file Double-click it Click Next through the installer
Mac
Download the .pkg file Double-click it Click Continue through the installer
Tip Accept every default option. There is nothing to choose or configure.
Step 2Check Node installed properly

Close your terminal completely and open a new one first. A terminal that was open before the install won't know Node exists yet — this catches almost everybody.

> node -v v20.11.0 ← a version number; yours may differ > npm -v 10.2.4 ← another version number
The point The exact numbers do not matter. Seeing a number instead of an error is the whole test.
If you see "not recognized" or "command not found"

Nine times out of ten the terminal was open before you installed Node. Close it, open a brand new one, and try again. If it still fails, put your hand up — don't fight it alone.

Step 3Install OpenCode

One command, identical on both Windows and Mac.

> npm install -g opencode-ai
You should see Text scrolling for up to a minute, ending with a summary. Yellow warnings are normal and can be ignored — only red errors matter.

The -g means "global" — install it for the whole computer rather than one folder. That's what lets you run it from anywhere.

Step 4Get your own free Gemini key

This part happens in your web browser, not the terminal.

1. Go to aistudio.google.com/apikey 2. Sign in with your Google account 3. Click Create API key 4. Copy the whole key
You should see A long string of letters and numbers. Copy every character — a missing one is the most common cause of the next step failing.
Treat it like a password

This key is yours alone. Don't post it anywhere or share it with anyone. It costs nothing, and if you ever lose it you simply create another.

Step 5Start the agent and connect your key

Back in the terminal, and make sure you're inside your my-agent folder.

> opencode the agent starts up > /connect use the arrow keys to choose Google, press Enter, then paste your key and press Enter again
Paste tip Use Ctrl + V on Windows or Cmd + V on Mac. Some terminals show nothing at all while you paste a key — that's normal and doesn't mean it failed. Just press Enter.
Step 6Your first instruction
> create a file called hello.txt containing a friendly greeting for a teacher, then show me what you wrote
You should see The agent thinking, creating the file, then showing you what it wrote. Type dir or ls afterwards and hello.txt will be there.
✋ Checkpoint

You now have a real file, created by an AI agent, on your own laptop. If you got here — everything else today is easier than what you just did.

Make a spare key before you forget

Free keys have daily limits. On Day 4 everyone will be working hard at the same time and somebody will hit theirs. A spare turns a stuck afternoon into a thirty-second fix.

1. Back to aistudio.google.com/apikey 2. Click Create API key a second time 3. Save both somewhere you can find them — a note on your phone is perfectly fine
Part 3

Teaching Your Agent

Three things that turn a generic agent into one that understands your work: standing rules, a shortcut, and a method.

1. AGENTS.md — your project's standing rules

Your agent starts fresh with every instruction. Without help you end up repeating the same background all day long.

Without it

"Add a page. Remember, plain HTML, no frameworks, keep files in this folder, ask before installing…"

Typed again. And again.

With it

"Add a page."

The background sits in a file the agent reads before every task.

Do nowAsk your agent to write it for you
> create an AGENTS.md file for this project. Stack: plain HTML and CSS, no frameworks. Rules: keep all files in this folder, use simple language in comments, and ask me before adding anything new.
You should see A new AGENTS.md file with your stack and rules under headings. Ask it to show you the contents if it doesn't do so automatically.

Here is roughly what it will contain. Notice there is nothing technical about it — it's a plain text file you could have written in Notepad.

AGENTS.md
# My Agent Project ## Stack - Plain HTML and CSS - No frameworks ## Rules - Keep all files in this folder - Use simple language in comments - Ask before adding anything new
Do nowProve it actually works
> make a simple welcome page for my class
Watch for You said nothing about HTML, frameworks or where to save it — but it followed all three rules anyway, because it read your AGENTS.md first.
Remember it as

The note you leave for a substitute teacher. Written once, so you don't have to explain it every morning.

2. Commands — your own shortcuts

AGENTS.md is background that always applies. A command is an action you deliberately fire when you want it. Both are ordinary text files.

The clever part: the filename becomes the shortcut. A file called course-outline.md gives you /course-outline. This is the same command you saw on Day 1.

Do nowCreate the course-outline command
> create a command called course-outline. It should write a one-page course outline for whatever topic and year group I give it, with who it is for, 3 to 5 learning outcomes, 4 to 6 sessions, and one way to check they learned it. Use $ARGUMENTS for the topic.
You should see A new file at .opencode/commands/course-outline.md. The dot at the front simply means the folder is normally hidden — nothing unusual about it.

Your file should look like this. The complete version is in Section 9 if you'd rather copy it than have the agent write it.

.opencode/commands/course-outline.md
--- description: Create a short course outline for a topic argument-hint: [topic and year group] --- Write a one-page course outline for: $ARGUMENTS Include who it is for, 3-5 learning outcomes, 4-6 sessions, and one way to check they learned it.
The important bit: $ARGUMENTS

That single word is the blank you fill in. Whatever you type after the command name drops into that spot — which is what makes one file work for every topic you will ever teach. Without it, you'd have a command that only ever writes about one subject.

Do nowRun it twice, with different topics
> /course-outline spreadsheets, Grade 10 then run it again with something else — > /course-outline internet safety, Grade 7
You should see Two completely different outlines, both in the same shape — and you typed the instructions zero times.
Remember it as

A lesson template you saved last year. You don't rewrite the plan each term — you open the saved one and go. And because it's a file, you can email it to a colleague.

3. Skills — a method, not just an instruction

A command saves an instruction you already know how to write. A skill gives your agent a whole method — the steps to follow for a kind of job. We'll build one, then watch it change how your agent behaves.

Do nowBuild the idea-refine skill
> create a skill called idea-refine. Its method: ask me 3 to 5 short questions, offer two or three directions, then write a one-page specification. Rule: never skip the questions.
You should see A new folder with a file inside it — .opencode/skills/idea-refine/SKILL.md. Skills are folders; commands are single files.

Only two lines are genuinely required — name and description. Everything below them is just markdown you wrote. The full file is in Section 9.

.opencode/skills/idea-refine/SKILL.md
--- name: idea-refine description: Refines a rough idea into a sharp, actionable concept by asking questions first --- ## How it works 1. Ask 3 to 5 sharpening questions, then wait 2. Offer two or three different directions 3. Write a one-page summary ## Rules - Never skip the questions - Always include what we are NOT doing
Do nowNow watch your own file change its behaviour

You never mention the skill by name. The agent reads the description, recognises the job, and follows your method by itself.

> help me refine an idea for a classroom activity about online safety
Watch for It should ask you questions instead of answering — because your file told it to. If it answers straight away, tell it: use the idea-refine skill.
Remember it as

A marking rubric from an experienced colleague. You don't work out how to assess the essay — someone already wrote down a good procedure, and you follow it.

Part 4

The Workflow

One method for building anything bigger than a single request — and the exact method you'll use to build a real application on Day 4.

Never ask for something big in one go

Asking for a whole project in one sentence gives you a vague result that's hard to correct. Four smaller steps give you something you actually wanted — because each arrow between them is a chance to catch a misunderstanding while it's still cheap to fix.

StepWhat you getWhy it helps
1. Rough ideaOne sentence.Where everyone starts. Nothing wrong with it.
2. SpecificationWhat exactly — and what deliberately not.Forces the vague parts into the open early.
3. PlanThe approach, in order.You can correct a plan in one sentence. Correcting finished work costs the whole build.
4. TasksSmall, checkable steps.Progress becomes visible, and mistakes stay small.

There is one skill for each stage, so you don't have to remember how each one works. You built the first this morning; now let's make the other two.

StageSkillWhat comes out
1. Sharpen the ideaidea-refineA clear one-page summary of what you actually want.
2. Agree what to buildwrite-prdA PRD — six sections, including what you're not doing.
3. Break it into stepsplanning-and-task-breakdown4 to 8 tasks, each with a Do and a Done line.
Do nowCreate the other two skills

You already know how, so this is quick — one prompt makes both. The complete files are in Section 9 if you'd rather copy them.

> create two more skills. write-prd — takes a refined idea and writes a one-page PRD with six sections: what we are building, who it is for, why, what it must do, what we are NOT doing, and how we know it is done. planning-and-task-breakdown — takes a PRD and turns it into 4 to 8 numbered tasks, each with a Do line and a Done line.
Then check Ask list my skills — you should have three.
.opencode/skills/
idea-refine/SKILL.md ← step 1 write-prd/SKILL.md ← step 2 planning-and-task-breakdown/SKILL.md ← step 3
Do nowStep 1 — sharpen the idea

Pick something you'd genuinely like for your own class. Real needs work far better than invented examples.

> use the idea-refine skill on this idea: a set of revision materials for my Grade 10 ICT class on spreadsheet formulas
Watch for It asks 3 to 5 questions, then offers two or three directions and recommends one. Answer honestly and pick a direction — the questions are the valuable part.
Do nowStep 2 — turn it into a PRD

A PRD — product requirements document — is just a written agreement about what you're making, before anyone starts making it.

> now use the write-prd skill to turn that into a PRD
You should see A one-page document with six sections. Read section 5 carefully — "what we are not doing" is the part that stops the work quietly growing until it never finishes.
Do nowStep 3 — break it into tasks
> use the planning-and-task-breakdown skill on that PRD
You should see 4 to 8 numbered tasks in order, each with a Do line and a Done line — so you can always tell what finished looks like.
what comes back
Task 1 — Write the practice questions Do: 10 questions on formulas, easy to hard Done: 10 questions exist with an answer key Task 2 — Add a worked example for each Do: show the steps, not just the answer Done: every question has a worked example

Read the tasks before accepting them. Correcting a task list takes a sentence; correcting finished work takes the whole build again.

Step 4 — iterate. This is the job, not a failure.

What beginners do

The output isn't right, so they delete everything and start the whole request again.

Slow — and it throws away the parts that were fine.

What you do now

"Good, but the questions are too easy for Grade 10, and I need a marking scheme at the end."

Keeps what worked. Changes only what didn't.

The rule of the week

Don't start over. Say what's wrong. You'll rely on this heavily on Day 4 — and it's the habit that most separates people who find these tools useful from people who give up on them.

Section 6

How to tell it actually worked

The agent will tell you it's finished. Confirming that independently is your job — it's the "you check" step of the loop, and it stays human.

  • Did it say it finished? Look for a clear success line. If it stopped mid-sentence, something went wrong.
  • Do the files exist? Type dir or ls and look for the filenames it claimed to create.
  • Does it run? If it started a web page, open the address it gave you — usually http://localhost:3000.
  • Is it what you asked for? Not just "does it work" but "does it do what I described". Re-read your own prompt.
A note on localhost

localhost means "this computer". A page at http://localhost:3000 runs on your own machine — nobody else can see it, and it disappears when you stop the program. That's exactly what we want all week.

If you're unsure, you're allowed to just ask:

> did that work? show me the files you created and confirm everything is running
Section 7

Repeating this setup somewhere else

The whole of today's setup, condensed. Use this on a school computer, at home, or when showing a colleague.

  1. Install Node.js LTS from nodejs.org — the .msi on Windows, the .pkg on Mac.
  2. Open a fresh terminal and check with node -v and npm -v.
  3. Run npm install -g opencode-ai.
  4. Get a free key at aistudio.google.com/apikey.
  5. Make a project folder with mkdir, then cd into it.
  6. Run opencode, then /connect, choose Google, paste the key.
  7. Test it with a small request, such as creating a text file.
Teaching this to students

These seven steps are the same ones your students would follow. The only part needing an adult is the Google account for the key — worth planning before a class, not during one.

Section 8

When something goes wrong

Every one of these is normal and fixable. None mean you've broken your computer, and none are your fault.

What you seeWhat it meansWhat to do
'opencode' is not recognized The computer can't find the agent. Close the terminal, open a new one, try again. If it persists, run the install command from Step 3 again.
'node' is not recognized Node isn't installed, or the terminal hasn't noticed it. Close the terminal and open a fresh one. If it still fails, reinstall Node from nodejs.org.
command not found: npm The Mac version of the message above. Close Terminal, reopen, try again.
429 / rate limit / quota You've asked the free service for too much too quickly. Nothing is broken. Wait a minute and continue. If it keeps happening, switch to your spare key with /connect.
401 / invalid API key The key wasn't accepted. Almost always a copy-paste problem — a missing character or a stray space. Run /connect and paste it again carefully.
EADDRINUSE / port in use Something is already running at that address, often an earlier attempt. Press Ctrl + C in the window still running it, or ask the agent to use a different port.
Cannot find module … Something the project depends on hasn't been downloaded. Tell the agent exactly that and ask it to fix it. It knows what to do.
Permission denied The folder doesn't allow changes. You're probably in a protected system folder. Make a folder in Documents and start again from there.
Nothing appeared when I pasted my key Many terminals hide pasted keys deliberately. Normal. Press Enter once — don't paste repeatedly.
It stopped halfway through Usually a rate limit or a brief network drop. Say "please continue". It picks up where it left off; you don't lose earlier work.
My command doesn't run The file may be in the wrong folder or named differently. Ask: "list my commands and tell me why /course-outline isn't working".
The universal fix

For anything not on this list — copy the whole error message and paste it to your agent, with a sentence saying what you were trying to do. Reading and fixing error messages is exactly what it's best at. You never have to decode one alone.

Everything you built today, in full. Your agent wrote these for you in the session — these are here so you can recreate them later, share them with a colleague, or fix one that didn't come out right.

--- name: write-prd description: Turns a refined idea into a short PRD - a written agreement saying what we are building, for whom, and what done looks like. Use after the idea is clear and before breaking work into tasks. --- # Write PRD A PRD is a written agreement about what we are building, before anyone starts building it. Keep it to one page. ## Before writing If any of these are unclear, ask me — do not guess: - Who will use this? - What problem does it solve for them? - What are we deliberately leaving out? ## Produce a document with exactly these sections ### 1. What we are building One sentence. If it needs two, it is not clear enough yet. ### 2. Who it is for The actual people — year group, role or audience. Not "users". ### 3. Why it is worth doing The problem it solves, in two or three lines. ### 4. What it must do A numbered list. Each requirement must be **checkable** — someone should be able to look at the finished thing and say yes or no. ### 5. What we are not doing A numbered list, each with a short reason. If it runs longer, cut requirements, not sections. - No vague requirements such as "should be user friendly". - Section 5 is mandatory. A PRD without it is a wish list. - Plain language — someone outside the project should be able to follow it. ## Next step Once the PRD is agreed, use **planning-and-task-breakdown** to turn each requirement into small, ordered tasks.

--- name: planning-and-task-breakdown description: Breaks work into small ordered tasks with clear acceptance criteria. Use when you have a PRD or clear requirements and need to turn them into steps you can actually start and finish. --- # Planning and Task Breakdown Turns an agreed PRD into tasks small enough to finish and check one at a time. ## How to break the work down 1. Read the PRD's requirements. Each one becomes **one or more tasks**. 2. Put the tasks in the order they must happen — nothing may depend on a task that comes later. 3. Make each task small enough to finish in one sitting. ## Every task must have - **A number and a short name** — so we can refer to it - **What to do** — one or two plain sentences - **How we know it is done** — something you can look at and confirm ## Output format ``` Task 1 — [short name] Do: [what happens] Done: [what you can check] ``` ## Rules - If a task cannot be checked, it is not a task — rewrite it. - If a task feels too big to start, split it in two. - Aim for 4 to 8 tasks. More than that usually means the PRD is too big. - Do not start building. Produce the list, then stop and let me review it. ## Next step Work the list one task at a time, confirming each is done before moving on.
Worth knowing

Every one of these is an ordinary text file. Nothing is compiled, nothing is installed, and nothing breaks if you edit one. If a skill isn't behaving how you want, open it and change the wording — that is the whole mechanism.
