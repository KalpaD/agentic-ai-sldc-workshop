# Write PRD

A PRD is a written agreement about what we are building, before anyone starts
building it. Keep it to one page.

## Before writing

If any of these are unclear, ask me — do not guess:

- Who will use this?
- What problem does it solve for them?
- What are we deliberately leaving out?

## Produce a document with exactly these sections

### 1. What we are building
One sentence. If it needs two, it is not clear enough yet.

### 2. Who it is for
The actual people — year group, role or audience. Not "users".

### 3. Why it is worth doing
The problem it solves, in two or three lines.

### 4. What it must do
A numbered list. Each requirement must be **checkable** — someone should be able
to look at the finished thing and say yes or no.

### 5. What we are not doing
A numbered list, each with a short reason. This section stops the work quietly
growing.

### 6. How we will know it is done
Two or three plain checks that prove it works.

## Rules

- One page. If it runs longer, cut requirements, not sections.
- No vague requirements such as "should be user friendly".
- Section 5 is mandatory. A PRD without it is a wish list.
- Plain language — someone outside the project should be able to follow it.

## Next step

Once the PRD is agreed, use **planning-and-task-breakdown** to turn each
requirement into small, ordered tasks.
