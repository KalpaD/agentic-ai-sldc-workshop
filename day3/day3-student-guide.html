Part 1

Context Engineering

A grand name for a simple idea: deciding what your agent knows before it answers. This is the difference between an agent that feels clever and one that feels useless.

What context actually is

Context is everything your agent can see at the moment you press Enter. Not everything it has ever read — everything in front of it, right now. It answers using that, and nothing else.

What people assume

"It knows my project. I told it about the bakery an hour ago."

So they write short prompts, and wonder why the answers drift.

What is actually true

It knows exactly what is in front of it: your message, your AGENTS.md, the files it has opened, and the conversation so far.

Anything outside that does not exist to it.

The mental model to break

Your agent does not remember like a person does. It re-reads. Everything else in this section follows from that one correction.

The four things that fill the context

What goes inWho controls it
1. What you just typedYou — every time.
2. Your AGENTS.mdYou — written once, re-read before every task.
3. Files it has openedYou, by naming which files you mean.
4. The conversation so farYou, by choosing when to start fresh.

You control all four. That is the whole of context engineering — the rest is just knowing when to use which.

Why the window runs out

Remember tokens from Day 1? The context window holds a fixed number of them. Fill it up, and the oldest parts get pushed out to make room — which is exactly when an agent starts "forgetting" something you agreed earlier.

WhenWhat's happeningWhat you notice
Early in a chatPlenty of room.Answers feel sharp. It remembers everything.
An hour laterThe window is full of old messages.Your important rule from earlier has been squeezed out.
The symptomNothing is broken — the window is simply full.It contradicts itself, forgets the file structure, or re-does work.

You will meet this on Day 4. When you do, it is not a fault and it is not your mistake — it is a full window, and the fix is in the checklist below.

Weak context vs strong context

Identical prompt — six words. The only difference is what the agent could see when it answered.

Weak — fresh session, nothing else

"add a contact section"

What comes back: a contact form with name, email and message. Styled in a way that matches nothing. Saved wherever it felt like.

It guessed, because it had to.

Strong — AGENTS.md + the page open

"add a contact section"

What comes back: a section matching the page's fonts and colours, with the bakery's real phone number, added to the existing file.

Same six words. Much better answer.

Technique 1 — write the rules down once

You did this yesterday. AGENTS.md is the single highest-value thing you can put in context, because it is re-read before every task and never gets squeezed out.

One thing people miss: style is context too. Most assume AGENTS.md is only for technical facts, but telling it the tone you want genuinely changes the words and colours it chooses.

Technique 2 — point at the file you mean

Vague

"make the heading bigger"

Which heading, in which file? It may open three files looking, or change the wrong one.

Pointed

"in index.html, make the main heading at the top bigger"

One file, one change, checkable in seconds.

Four extra words, and it also keeps the window tidy — because the agent stops opening files speculatively.

Technique 3 — start fresh when you change job

A long conversation carries everything before it. When you move to a new task, that old detail is no longer help — it is clutter competing for space.

  • Keep the same session while you're still on the same thing — building the page, then fixing the page, then styling the page. The history is genuinely useful.
  • Start a new one when you switch to something unrelated — from the bakery page to marking a quiz. Type /new and begin clean.
Think of it as

Wiping the whiteboard between two lessons. Not because the last lesson was wrong — because leaving it up confuses the next one.

Starting a new session costs nothing and loses nothing from disk. Your files are all still there.

Technique 4 — give it enough, not everything

The instinct once you understand context is to pour in as much as possible. That backfires: the important detail gets buried among the unimportant.

Too much

Pasting a whole textbook chapter, every file in the folder, and three previous lesson plans — to ask for one paragraph.

The one line that mattered gets lost.

Enough

The relevant file, the rule that applies, and a clear request.

Nothing competing for its attention.

More context is not better context. Relevance beats volume every time.

The checklist — when an answer disappoints

Ask yourselfThe fix
Did it know the rules of this project?Put them in AGENTS.md — once, permanently.
Did it know which file I meant?Name the file in your request.
Have we been talking for a long time?Start fresh with /new.
Did I bury the important part?Cut the rest. Give it what matters and nothing else.
The most useful sentence of the day

Nine times out of ten, a disappointing answer is a context problem, not a model problem. Work through these four questions before you conclude the tool isn't good enough.

Part 2

Many Hands

Once you understand context, sub-agents make sense — because the real reason to split a job is to give each part its own clean context.

You already have helpers — you don't build them

OpenCode ships with these. You call one by typing @ and its name, exactly like tagging a colleague in a message.

HelperWhat it's forWhat it may do
@exploreSearches your files and reports back.Read-only — it cannot change anything.
@scoutLooks things up outside your project.Read-only.
@generalTakes on a whole piece of work on its own.Full access.
Why read-only matters

You can hand @explore a job with no risk at all. It can tell you what's wrong with your page, but it cannot touch it. We use exactly that as our reviewer in the build.

The real reason to split a job

Sub-agents produce better work not because they are cleverer, but because each one gets its own clean context and only sees what its own job needs.

HelperWhat it sees
Writes the wordsThe brief only.
Builds the layoutThe words and the rules — not the conversation about writing them.
Checks the workThe finished page and the rules.
Think of it as

Group work in your classroom. You don't give every group the whole project brief — you give each the part they need, then bring the pieces together yourself.

Keeping them aligned

Three helpers working separately can easily produce three styles that don't match — formal words, playful layout, and a reviewer judging it against something else entirely.

There is one thing that keeps them aligned, and you already have it: every helper reads the same AGENTS.md before starting. Same stack, same tone, same rules. That is why we write it first in the build, before any helper is called.

When not to bother with helpers

Splitting a job has a cost — you have to brief each helper and join the pieces up. For small work that cost is more than the benefit.

Don't split

"Fix this typo."
"Make the heading bigger."
"Add my phone number."

One agent, one message. Done.

Do split

Work with clearly different jobs inside it — writing versus building versus checking. Or when you want a reviewer who cannot change your work.

Worth the briefing.

Part 3

Build It — Sunrise Bakery

Six steps. A small family bakery with no website at all — customers only find them by walking past. They want one simple page they can send people to.

The brief
What they sellBread, buns, and birthday cakes to order.
Who visitsNeighbours, mostly on a phone.
What they needOpening hours, what's on offer, how to contact them.
TomorrowWe build the cash-flow tracker the owner uses behind the counter.
Step 1A folder, and the rules everyone follows

Start from the my-agent folder you made yesterday.

> mkdir bakery > cd bakery > opencode

Then, inside the agent, ask it to write the shared rules. Every helper will read this file.

> create an AGENTS.md for a one-page website for Sunrise Bakery. Stack: one index.html and one style.css, plain CSS, no frameworks, no JavaScript. Style: warm, friendly, simple, big readable text. Rules: keep all files in this folder, ask before adding anything new.
Check Run dir or ls — you should be inside a bakery folder containing AGENTS.md and nothing else.
Don't skip the new folder

If you build the bakery inside yesterday's project, the agent picks up yesterday's AGENTS.md and the page comes out wrong in confusing ways. A fresh folder means fresh rules.

Step 2First helper — write the words

Notice we ask for only the words. No HTML yet. One job, one helper, one clean context.

> @general write the words for the Sunrise Bakery page and save them in content.md. We need: a short welcome, what we sell, opening hours, and how to contact us. Warm and friendly. Words only — no HTML.
You should see A new content.md with real sentences in it. Read them — this is the bakery's voice being decided.
It invented the phone number

Expected, and a perfect live example of why context matters. The brief didn't include one, so it filled the gap. You'll replace it later — but notice that a thin brief produces invented detail every time.

Step 3Second helper — build the page around those words

This helper's context is different: it needs the words and the rules, but not the conversation about writing them.

> @general using the text in content.md, build index.html and style.css for the Sunrise Bakery page. Follow AGENTS.md. Make it work well on a phone. Warm colours, big readable text.
Check Run dir or ls — you should now have four files: AGENTS.md, content.md, index.html, style.css.

You named the file — technique 2 from this morning — so this helper never had to guess where the words were.

Step 4Open it in your browser
> open index.html in my browser
Or do it yourself Find the bakery folder in your file manager and double-click index.html.

A real web page, on screen, that you described but never wrote. This is the first thing this week that a stranger could look at.

Step 5Third helper — a reviewer that cannot break anything

Here is where read-only earns its keep. @explore can read every file and tell you what's wrong, but it physically cannot change your page.

> @explore read index.html, style.css and AGENTS.md, then tell me anything that breaks the rules in AGENTS.md or looks wrong on a phone. Just report — do not change anything.
You should see A short list of problems. Common ones: a framework crept in, text too small on a phone, or a section from content.md that never made it onto the page.

If the review finds nothing at all, it probably didn't really look. Ask it to check against each rule in AGENTS.md one at a time.

Step 6Hand the findings back to be fixed

The reviewer found the problems. The main agent fixes them — exactly how a real team works.

> fix everything on that list, then tell me what you changed

Refresh the page in your browser, then check again:

> @explore check it again
Watch for The second review should be shorter than the first. That gap is the whole value of having a reviewer.

Make it yours

Change whatever you like. Try one thing at a time and refresh the browser after each — that habit is what makes problems easy to find.

  • Make it real — "Change the opening hours to 6am–7pm and the phone number to my school's."
  • Change the feel — "Make the colours cooler and more modern." Then ask for warm again and compare.
  • Add something — "Add a section listing three cakes with prices." Watch it obey AGENTS.md while doing it.
The rule of the week, again

Don't start over. Say what's wrong and let it fix that one thing. You'll rely on this completely tomorrow.

What just happened, in order

StepWho did itWhat it saw
Set the rulesYouThe brief in your head.
Wrote the words@generalThe brief and the rules.
Built the page@generalThe words and the rules — not the writing conversation.
Reviewed it@exploreThe finished files and the rules. Read-only.
Fixed itMain agentThe review findings.

Nobody saw more than their job required. That is the whole technique.

Section 7

When something goes wrong

Today's problems are different from yesterday's — these are the ones that come up when building a page.

What you seeWhat it meansWhat to do
The page looks plain — no colours or spacing The HTML isn't loading the CSS file. Ask: "index.html doesn't seem to be using style.css — please check and fix the link."
My changes don't show in the browser You're looking at the old version. Refresh the page. If it still looks the same, hold Shift and refresh to force it.
It used a framework despite the rules It didn't read, or didn't follow, AGENTS.md. Say: "AGENTS.md says no frameworks. Please redo this using plain CSS only."
@explore found nothing wrong It gave the files a shallow look. Ask it to check against each rule in AGENTS.md one at a time.
A helper ignored the rules completely You're probably in the wrong folder. Run dir or ls — if you can't see AGENTS.md, you're not in the bakery folder.
It's forgotten what we agreed earlier The context window is full. Start fresh with /new. Your files are all still on disk.
The page won't open at all Wrong file, or it was never created. Run dir or ls and check index.html is actually there.
The universal fix, still

For anything not on this list — copy the whole message and paste it to your agent, with a line saying what you were trying to do. You never have to work it out alone.
