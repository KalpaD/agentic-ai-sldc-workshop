Part 1

AI & Generative AI

Before we talk about agents, let's be precise about what the thing underneath them actually is — and what it isn't.

Ordinary software follows rules. AI learns patterns.

This one difference explains everything that follows. Ordinary software does exactly what a human being wrote down in advance. If a situation comes up that the programmer didn't think of, the software has no answer.

AI software is built differently. Nobody writes the rules. Instead the system is shown an enormous number of examples and works out the patterns for itself — which means it can handle situations nobody specifically prepared it for.

Ordinary software

A person writes every rule by hand:

IF subject contains "lottery"
THEN mark as spam

A new kind of spam arrives that doesn't mention lottery. It goes straight to the inbox, because no rule covers it.

AI software

Nobody writes any rules. The system is shown thousands of emails already labelled spam or not-spam, and works out for itself what spam tends to look like.

The new kind of spam still gets caught, because it resembles the pattern — even though no human described it.

What the word "generative" adds

Older AI systems mostly decide something: which category, which label, yes or no. Generative AI creates something that did not exist before. The difference is the shape of what comes out.

TypeYou askYou get back
Deciding AI"Is this email spam?"Yes, or no. A choice from a fixed set.
Deciding AI"What language is this?"Sinhala. Again — a choice.
Generative AI"Write a reply to this parent."A complete paragraph that never existed before.
Generative AI"Build me a webpage."Working code that never existed before.

Everything we do this week lives in that bottom half of the table.

How it actually works: predicting the next piece

This is worth understanding properly, because it explains both why generative AI is impressive and why it sometimes gets things wrong.

A generative AI is not looking answers up in a database. It has read an enormous quantity of text and learned which words tend to follow which other words. When you ask it something, it predicts the most likely next word — then, having written that, predicts the next one, and so on.

how a sentence gets built
"The capital of Sri Lanka is Sri … Jayawardenepura … Kotte" each word chosen as "most likely to come next", given everything before it
Why this matters all week

Because it produces what sounds most likely rather than looking up a verified fact, it can occasionally state something wrong with complete confidence. This isn't a fault you caused — it's a property of how the technology works. It's the reason you always check the result yourself.

Those pieces have a name: tokens

An AI model doesn't see letters, and it doesn't see whole sentences. It breaks text into chunks called tokens. A common word is usually one token; a longer or less common word gets split into several pieces.

A simple sentence — every common word is one token
Thecatsatonthemat. 7 tokens
A longer word gets broken into pieces
Photosynthesisisfascinating. 6 tokens

As a rough guide, 4 characters ≈ 1 token, so about 750 words ≈ 1,000 tokens. The exact split differs between AI models. You never need to count tokens yourself — but it helps to know the unit exists, because everything else is measured in it.

Tokens in, tokens out

Your question is turned into tokens before the model ever sees it. The model then produces its answer one token at a time, and those are turned back into words on your screen. That is the whole cycle:

StageWhat happens
You type"Explain photosynthesis"
Input tokensYour words are chopped into tokens the model can read.
The modelPredicts the next token, over and over.
Output tokensThose tokens become the answer you read — which is why answers appear word by word rather than all at once.
Why you'll care on Day 2

Everything is measured in tokens, including the free allowance we all use this week. When your agent pauses and mentions a rate limit, it means too many tokens were sent too quickly. Nothing is broken — you now know exactly what that message means.

Where you already see it

  • Text — lesson plans, exam questions, letters to parents, report comments, translations.
  • Images — illustrations for worksheets, diagrams, slide backgrounds, poster art.
  • Code — working software: websites, apps, databases. This is our focus for the rest of the week.

Here's something that surprises people: code is one of the things generative AI is best at. Code has strict, checkable rules — the machine can run what it wrote and immediately find out whether it worked. An essay has no such test. That ability to check its own work is exactly what makes coding agents possible.

Part 2

Coding Agents

The heart of today. We go slowly here — most people have never seen one of these work, so we look at what it does before we name anything.

The problem with chat AI

Suppose you ask ChatGPT to build a page for your school's sports day. It will happily write the code. But look at what you personally still have to do afterwards.

With chat AI — eight steps, all yours

1. It prints code into the chat window.
2. You select and copy it.
3. You open a text editor.
4. You paste it, and save it with exactly the right filename in exactly the right folder.
5. You open it in a browser.
6. Something looks wrong.
7. You copy the error message back into the chat.
8. Repeat, several times.

With a coding agent — one step

1. You say what you want.

It creates the file itself, in the right folder, with the right name. It runs it. If something breaks, it reads its own error message and fixes it — then tells you it's finished.

You never left the one window.

First, what a terminal is

Coding agents live in a plain text window called the terminal — on Windows it may be called Command Prompt, PowerShell or Terminal; on a Mac it's called Terminal. If you have never opened one, that's completely normal and nothing to be embarrassed about.

It is simply a different way of asking your computer to do things.

The way you already know — pointing

You see folders and icons on screen. You move the mouse, double-click, and drag things around to make things happen.

You point at what you want.

The terminal — typing

The same computer, the same files, the same folders. But instead of clicking, you type a line describing what you want, and press Enter.

You describe what you want.

Don't worry

You will not need to memorise commands. Tomorrow we practise the handful you actually need — they're listed in Section 5 of this guide — and after that, your agent does nearly all the typing for you.

A real session, line by line

Here is what a short conversation with a coding agent looks like. Read it top to bottom; the notes underneath explain each part.

terminal
> build a page that shows today's date and a friendly greeting Reading your project… Creating index.html… Writing the greeting logic… Running it… ⚠ Error: greeting is not defined Fixing… ✓ Done — open http://localhost:3000
  1. 1
    You type plain English.No code, no special syntax, no memorised keywords. Exactly how you'd ask a colleague to do something.
  2. 2
    It looks around first."Reading your project" means it opens what's already in your folder, so its work fits with what's there rather than guessing.
  3. 3
    It creates real files.After "Creating index.html", that file genuinely exists on your computer. Nothing was copied or pasted by you.
  4. 4
    It hit an error — and fixed it.This is the part chat AI cannot do. It ran the code, saw its own mistake, and corrected it without being asked. This is the single biggest difference.
  5. 5
    It tells you how to check.The last line gives you an address to open in your browser so you can confirm with your own eyes that it worked.

The loop underneath everything

What you just read follows the same four steps every time — whether the task takes ten seconds or an hour.

  1. You describe what you want, in ordinary language.
  2. It plans — works out which steps are needed and in what order.
  3. It acts — writes files, runs them, reads any errors, fixes them.
  4. You check — is this actually what you wanted?

Then it goes round again. If you're not happy, you don't start over: you say what's wrong, and the loop repeats from step one. The agent never decides it's finished — you do.

What the agent is actually allowed to do

A chat window can only produce text on a screen. An agent is that same AI, plus permission to touch your computer in four specific ways.

PowerWhat that means in practice
ReadOpen and understand files already in your project, so new work fits with what exists.
WriteCreate new files and edit existing ones, directly on your machine.
RunActually execute what it wrote — start the program, open the page, run the tests.
ObserveSee the result or the error message that came back, and use it to correct itself.

That fourth one is what makes it feel like a colleague rather than a tool: it closes its own loop.

A fair question

"Is it safe to let a program write files on my computer?" Yes, with two protections: it works inside the project folder you started it in, and it asks your permission before anything significant. You can always see exactly what it changed. We cover this properly tomorrow.

The tools you'll hear about

NameMade byNotes
Claude CodeAnthropicTerminal-based. Widely used by professional developers.
GeminiGoogleThe AI model we'll use this week, through a free key.
CodexOpenAIFrom the makers of ChatGPT.
CopilotGitHubLives inside a code editor rather than the terminal.

They all work on the same loop. Learning one means you can pick up any of them — which matters, because the tool your school uses in two years may not be the one we use this week.

What we'll use: OpenCode with a free Gemini key

Two separate pieces, and it's worth knowing why they're separate:

  • OpenCode — the agent itself. The program that runs the loop in your terminal. Open source and free.
  • A Gemini API key — the AI brain it talks to. You create your own from Google, with no credit card required.
Why two pieces

Because the agent and the brain are separate, a better AI model appearing next year doesn't mean relearning everything. You keep the same tool and point it somewhere new — and so can your students.

Part 3

Prompting — asking so you get what you wanted

The agent is only ever as good as the instruction you give it. This is the most immediately useful part of today — it will improve your ChatGPT results tonight, not just your coding next week.

You are briefing an assistant, not searching Google

With a search engine, fewer words is better — you're matching keywords, and you'll pick from a list of results yourself. With an AI, the opposite is true. There is no list to choose from: it builds exactly one thing, so it needs to know which one.

Search habit

sports day page

Three words is plenty, because you'll scan ten results and choose.

Briefing habit

"A page for our sports day on the 12th, with the event list, start times, and house colours down the side."

It makes one thing. Detail is what makes it the right one.

The same request, two ways

Weak prompt

"Make a form"

What comes back: some form, with some fields, styled some way. Probably not yours. You now spend ten minutes correcting it.

Strong prompt

"Make a form with name, date and amount fields. Show an error if amount is blank. Keep the styling simple — no frameworks."

What comes back: close to right, first time.

Three extra sentences saved ten minutes of correcting. That's the entire argument for learning to prompt well.

What made that prompt work: four parts

Take the strong version apart and you'll find four distinct pieces. If a prompt of yours disappoints, one of these is usually missing.

anatomy of a good prompt
1 Make a form 2 with name, date and amount fields. 3 Show an error if amount is blank. 4 Keep the styling simple — no frameworks.
  1. 1
    The taskWhat you want made. Most people stop here — this is the whole prompt for most beginners.
  2. 2
    The specificsThe exact pieces it should contain. Removes all the guessing.
  3. 3
    The behaviourWhat should happen in a particular situation — a rule, not just a thing.
  4. 4
    The boundaryWhat not to do. Frequently the most valuable line in the whole prompt.

A template you can reuse

fill-in-the-blanks prompt
Build [what] with [the specific parts it needs]. When [situation], it should [behaviour]. Don't [boundary].

Six named techniques

These are the standard techniques people mean when they say "prompt engineering". You already use some by instinct. Knowing the names means you can read any article about AI and follow it — and teach them to your students by name.

1. Zero-Shot — just ask, no examples

What everyone already does. Excellent for small tasks with only one sensible answer shape; quietly disappointing when you had a particular format in mind but never said so.

Where it lets you down

"Write 5 quiz questions on photosynthesis."

You get five questions — in whatever format and difficulty it chose. You didn't say, so it guessed.

Where it shines

"Summarise this paragraph in one sentence."

Simple and unambiguous. No examples needed.

2. Few-Shot — show two or three examples

The fastest way to get output in your style is to show your style rather than describe it. Keep two model questions in a file, ready to paste.

Describing your style

"Write quiz questions in my usual style."

It has never seen your papers. It cannot know what your usual style is.

Showing your style

"Here are two of my questions:

1. State two uses of a spreadsheet. (2 marks)
2. Explain why a formula begins with =. (3 marks)

Now write three more in exactly this style."

Marks, numbering and phrasing all get copied automatically.

3. Role / Persona — tell it who to be

Two sentences about who is speaking and who is listening changes the vocabulary, the depth and the examples it picks. The audience half matters more than the role half.

No role given

"Explain photosynthesis."

A competent encyclopaedia paragraph, pitched at nobody in particular.

Role and audience given

"You are a Grade 8 science teacher in Sri Lanka. Explain photosynthesis to a 13-year-old using an example from a home garden. Under 150 words, no technical terms."

Now it is pitched at your actual class.

4. Chain-of-Thought — make it show its working

Remember it predicts one token at a time. If you let it jump straight to an answer, it commits before it has reasoned. Asking for the steps first makes it reason on the way. Use this for anything with numbers, logic or marking.

Straight to the verdict

"A student answered 47 for this problem. Is that correct?"

A confident yes or no — sometimes the wrong one.

Working first, verdict after

"Solve this problem yourself, step by step. Then compare your answer with the student's 47, and tell me exactly where they went wrong."

A better answer — and an explanation you can mark from.

5. Least-to-Most — build up in small steps

For anything large, one giant request produces something shallow. Asking in sequence, where each answer feeds the next, produces something usable. This is the seed of the whole Day 2 and Day 4 workflow.

One giant ask

"Create a full term scheme of work for Grade 10 ICT."

Generic, thin, and wrong in ways that are tedious to correct.

Three asks, in order

1. "List the topics for a 10-week Grade 10 ICT term."

2. "For topic 1, list the learning outcomes."

3. "Now write week 1's lesson plan using those outcomes."

Each step checked before the next one starts.

6. Interview Style — make it ask you first

The most counter-intuitive, and often the best. Instead of describing everything up front, hand the questioning over and let it find the gaps. This is exactly what the idea-refine skill does on Day 2 and Day 4.

You guess what matters

"Make me a revision worksheet on spreadsheets."

It fills every gap with an assumption — year group, length, difficulty, format.

It finds the gaps for you

"Before you write anything, ask me five questions that would help you make this worksheet well. Then wait for my answers."

The gaps get found before the work, not after.

Which one, when

TechniqueReach for it when…Typical use
Zero-ShotThe task is small and there's one sensible answer shapeSummarise, translate, tidy up
Few-ShotThe output must match your format or styleExam questions, report comments
Role / PersonaThe pitch and audience matterExplaining a topic to a year group
Chain-of-ThoughtThere's reasoning, numbers or marking involvedChecking a student's working
Least-to-MostThe job is too big for one requestSchemes of work, whole projects
Interview StyleYou're not certain what you want yetStarting anything from scratch

You'll live in the first three. The last three come out when the job is bigger, or when the answer really has to be right.

Treat the first answer as a first draft

Even an excellent prompt often lands at about eighty percent. That is not failure — it's the normal working rhythm, and it's far faster than starting from a blank page.

What beginners do

The result isn't right, so they delete everything and rewrite the whole request from scratch.

Slow — and it throws away the eighty percent that was fine.

What to do instead

"Close. The date field should come first, and the error message should be red."

Keeps the good part. Fixes only what's wrong.

The rule for the whole week

When something isn't right, don't start over and don't try to fix it by hand. Tell the agent what you're seeing and ask it to fix it. You'll hear this on Days 2, 3 and 4 until it's automatic — because it's the actual skill this course is teaching.

Part 4

The five words you'll hear all week

For each one: the problem it solves, what it actually looks like on screen, and something familiar to compare it to. You'll create the first three yourself tomorrow.

The mental model

An agent is a loop wrapped around an AI model. The model in the middle only predicts text. The loop around it is what reads files, writes them, and runs things. Everything in this section is something you hand to that loop to make it work better.

1. AGENTS.md — the standing rules for your project

The problem it solves

The agent starts fresh with each new instruction. Without help, you end up repeating your project's basics again and again, all day long.

Every single prompt

"Add a delete button. Remember we're using NestJS, the database is SQLite, there's no login system, plain HTML, no frameworks…"

Repeated forty times a day.

Written down once

"Add a delete button."

All the background lives in a file the agent reads before every task.

What it actually looks like

It is a plain text file called AGENTS.md, saved at the top of your project folder. Here is a real one — very close to what you'll write tomorrow for the project you build on Day 4.

AGENTS.md
# Cash-Flow Tracker ## Stack - Backend: NestJS - Database: SQLite - Frontend: plain HTML and CSS, no framework ## Rules - No login or user accounts - Keep everything in one folder - Ask me before adding anything new
  1. 1
    It's just text.You could write this in Notepad. There is no programming involved, and nothing to install.
  2. 2
    The Stack sectionTells the agent which technologies to use, so it never guesses and never picks the wrong thing.
  3. 3
    The Rules sectionYour boundaries. "Ask me before adding anything new" is the single most useful line most people write.
  4. 4
    Read automatically.You never mention the file again. The agent checks it before every single task, for as long as the project exists.
Think of it as

The note you leave for a substitute teacher. Where things are, what the class is working on, what not to let them get away with — written once, so you don't have to explain it every morning.

2. Commands — a shortcut for an instruction you keep repeating

The problem it solves

This one isn't about project background — it's about a whole task you ask for again and again. Think of something you write every term: a course outline, in the same shape, for a different topic each time.

Every term, for every topic

"Write me a course outline on spreadsheets for Grade 10. Include who it's for, the learning outcomes, four to six sessions, and a way to check they learned it. Keep it to one page, plain language…"

Retyped, slightly differently, every time.

Saved once as a command

/course-outline spreadsheets, Grade 10

Next week, a different topic — same shape, same quality.

Easy to mix up

AGENTS.md is background that always applies, automatically. A command is an action you deliberately choose to fire when you want it.

What it actually looks like

A command is a text file, saved in a .opencode/commands folder. The filename becomes the shortcut — save course-outline.md and you can type /course-outline.

.opencode/commands/course-outline.md
--- description: Create a short course outline for a topic argument-hint: [topic and year group] --- Write a one-page course outline for: $ARGUMENTS Include who it is for, 3-5 learning outcomes, 4-6 sessions, and one way to check they learned it. Plain language, no jargon.

Then, in the terminal, you simply type:

terminal
> /course-outline spreadsheets, Grade 10 Writing outline…
  1. 1
    The filename is the shortcut.course-outline.md becomes /course-outline. Name it whatever makes sense to you.
  2. 2
    The top part is just a label.A description so you remember what it does, and an argument-hint reminding you what to type after the name. Both optional, both helpful.
  3. 3
    $ARGUMENTS is the blank you fill in.Whatever you type after the command name drops into that spot. That's what makes one file work for every topic.
  4. 4
    The rest is plain English.Exactly what you'd otherwise type by hand — and since it's an ordinary file, you can email it to a colleague.
You'll build this one tomorrow

A copy of this exact command is in your workshop folder as course-outline.md. On Day 2 you'll create your own version and run it on a topic you're actually teaching.

Think of it as

A lesson template you saved last year. You don't rewrite the whole plan each term — you open the saved one and go.

3. Skills — borrowing someone else's expertise

The problem it solves

A command saves an instruction you already know how to write. But what if you don't know the right way to do something in the first place?

Without a skill

"Help me plan an app."

You get something generic, because neither of you has agreed what "planning an app" actually involves.

With a skill

The agent already has an expert's step-by-step method for that job written down, and follows it: ask questions, explore options, narrow down, write a specification.

What it actually looks like

A skill is a folder with a file called SKILL.md inside it, saved under .opencode/skills/. Here is a real one — a copy is in your workshop folder, and you'll use it tomorrow and again on Day 4.

.opencode/skills/refine-idea/SKILL.md
--- name: refine-idea description: Turn a rough teaching idea into a clear one-page specification by asking questions first --- ## What I do - Ask you 3 to 5 short questions - Offer two or three possible directions - Write a one-page specification once you choose ## When to use me When you have a rough idea and are not yet sure what you actually want. ## Rules - Never skip the questions - Keep it to one page - Always include what we are NOT doing
  1. 1
    Only two lines are required.A name and a description. Everything below them is just markdown you write yourself.
  2. 2
    The description is the trigger.The agent reads it and recognises when your request matches this kind of job.
  3. 3
    The body is the method.Plain headings and steps, written down by someone who knows the craft properly.
  4. 4
    You don't have to call it by name.Ask for help with an idea, and the agent reaches for it by itself.
Think of it as

A marking rubric from an experienced colleague. You don't have to work out how to assess the essay — someone already wrote down a good procedure, and you follow it.

4. Sub-agents — focused helpers your agent can call

One agent doing everything has to hold too much in its head at once, and quality slips. Instead it hands focused pieces to helpers. The good news: OpenCode already comes with several, so you don't have to build any.

HelperWhat it's forWhat it may do
exploreSearching through your own files to find something.Read only — it cannot change your work.
scoutLooking things up outside your project, such as documentation.Read only.
generalTaking on a whole multi-step job on its own.Full access.

How you call one

Type @ followed by the helper's name — exactly like tagging a colleague in a message.

terminal
> @explore find every file that mentions the sports day page ⤷ explore · read-only searching… found 3 files > now summarise what it found

The helper does its one job, hands the answer back, and you carry on where you left off. Notice that explore is deliberately read-only — you can hand out a job with no risk of it changing your work.

Think of it as

Group work in your classroom. One group researches, one designs the poster, one presents — and you pull it together at the end. This is exactly the split you'll use on Day 3.

5. MCP — one standard way to plug in outside tools

Your agent knows about the files in your project folder. It does not automatically know about your school's database, your calendar, or anything else outside that folder. MCP — Model Context Protocol — is the agreed standard for connecting those things in, so that every tool doesn't need its own special wiring.

Think of it as

A universal travel adapter. Rather than a different plug for every country, one agreed shape fits them all. You won't need this during our four days — but you'll hear the word constantly, so now you know what it means.

Section 6

How to tell whether it actually worked

The agent will tell you it's finished. Your job is to confirm that independently — this is the "you check" step of the loop, and it's the part that stays human.

Four checks, in order

  • Did it say it finished? Look for a clear success line — a tick, the word "Done", or an address to open. If it just stopped mid-sentence, something went wrong.
  • Do the files exist? Type dir on Windows or ls on Mac and look for the filenames it claimed to create. If they aren't there, they weren't created.
  • Does it run? If it started a web page, open the address it gave you — usually http://localhost:3000 — in your browser. Seeing the actual page is the real proof.
  • Is it what you asked for? Not just "does it work" but "does it do what I described". Check your own prompt against what's on screen.
A note on localhost

localhost means "this computer". A page at http://localhost:3000 is running on your own machine, not on the internet — nobody else can see it, and it disappears when you stop the program. That's exactly what we want all week.

If you're not sure, just ask

You are allowed to ask the agent to check its own work, and it's often the fastest route:

terminal
> did that work? show me the files you created and confirm the page is running
Section 7

Common errors and what they actually mean

Every one of these is normal and fixable. None of them mean you've broken your computer, and none of them are your fault. Find the message, read the plain-English meaning, do the fix.

What you seeWhat it meansWhat to do
'opencode' is not recognized The computer can't find the agent program. It either isn't installed yet, or the terminal was open before you installed it. Close the terminal, open a new one, try again.
'node' is not recognized Node.js isn't installed, or the terminal hasn't noticed it yet. Same fix: close the terminal and open a fresh one. If it still fails, Node needs installing — we do this together tomorrow.
command not found: npm The Mac version of the message above. Close Terminal, reopen, try again.
429 / rate limit / quota exceeded You've asked the free AI service for too much too quickly. Nothing is broken. Wait a minute and continue. This is expected on a free key and will happen to somebody in the room.
401 / invalid API key The Gemini key wasn't accepted. Usually a copy-paste problem — a missing character or a stray space. Run /connect and paste it again carefully.
EADDRINUSE / port already in use Something is already running on that address — often an earlier attempt you didn't stop. Press Ctrl + C in the window that's still running it, or ask the agent to use a different port.
Cannot find module … A piece the project depends on hasn't been downloaded. Tell the agent exactly that: "I'm getting 'cannot find module X' — please fix it." It knows what to do.
Permission denied The folder you're in doesn't allow changes. You're probably in a protected system folder. Make a new folder in your Documents and start the agent from there instead.
The page won't open in the browser The program has stopped, or you have the wrong address. Check the terminal is still running — if it returned to a plain prompt, the program stopped. Restart it and re-read the address.
It stopped halfway through Usually a rate limit or a brief network drop. Say "please continue". It picks up where it left off — you don't lose the earlier work.
The universal fix

If you see a message you don't understand, copy the whole thing and paste it to the agent, with a sentence saying what you were trying to do. Reading and fixing error messages is exactly what it's good at. You never have to decode one alone.

Section 8

Where it will let you down

You'll meet all three of these this week. None are your fault, and none mean you did something wrong.

  • Confident mistakes. Remember it predicts likely-sounding text. Sometimes the likely-sounding thing is simply wrong — stated with total confidence. This is why you check the result yourself.
  • It pauses. Free accounts have limits. Occasionally it stops for a minute in the middle of a task. That's normal, not broken — wait, then carry on.
  • Different every time. Ask the same thing twice and you'll get two slightly different answers. Neither is a bug. It's why clear instructions matter more than luck.
Recap

If you remember three things

01

A coding agent doesn't just answer — it reads, writes, runs and checks its own work on your computer.

02

Task, specifics, behaviour, boundary. A clear instruction beats a clever one every single time.

03

The first answer is a first draft. Don't start over — say what's wrong and go round the loop again.
