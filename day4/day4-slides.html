Stage 2 of 5

Plan & Slice

Turning a specification into tasks — and the one decision about how to cut them up that changes everything.
Two ways to slice Run the skill The project rules
The slicing idea is the intellectual content of today. Give it proper time here; the build goes far better if they understand why the order is what it is.
The key decision

Two ways to cut up the same work

By layer — the obvious way

1. Build the whole database
2. Build all the endpoints
3. Build the whole page
4. Connect it up

Run out of time at step 2 and you have a database and no application.

Nothing works until everything works.
By feature — vertical slices

1. Make it run
2. Record a transaction
3. See it and the balance
4. Delete one

Run out of time at step 2 and you still have a tool that records money.

Every step ends with something usable.
This is the single most transferable idea of the day and it applies far beyond software - it is how you would plan a scheme of work too. Ask which column they would rather be in at the final bell.

Do now · The project rules

Stage 3 of 5

Build It

Fifty minutes. One task at a time, checked before the next one starts. Never two at once.
Task 1 — scaffold Task 2 — record Task 3 — see it
Longest stretch of the week. Set the pace expectation now: we move together, and the checkpoints are not optional.
How the new skill works

Build a bit, check it works, then build the next bit

That's the whole of incremental-implementation. It sounds obvious. It is the discipline almost everyone abandons the moment they're in a hurry.

The reason this matters: a bug in task 2 makes tasks 3, 4 and 5 wrong, and you will not know which change caused it. Checking each piece is what keeps debugging small.
